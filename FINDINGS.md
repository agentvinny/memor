# Findings: Is There a Single Tool That Does This?

**No.** After deep-diving nine candidate areas (see `research/` — `LANDSCAPE.md` is the index and comparison table), no existing project — including the two that market themselves most directly as "the answer" (EverOS, explicitly branded an "AI Agent Memory Operating System," and HydraDB, explicitly branded as solving "AI agent memory is a database problem") — satisfies the brief. This isn't a close call resolved by picking the least-bad option; every candidate is missing entire categories of the brief's requirements, not just falling short on polish.

## Why not the obvious "memory OS" candidates

- **EverOS** is real and technically substantive (Apache-2.0, documented MemCell/Episode/Fact schema, genuine hybrid retrieval) but only ingests what's explicitly pushed to it in conversation — zero environmental observation — and its officially-supported multi-harness path (the Claude Code plugin) defaults to EverMind's cloud, not self-hosting. Self-hosted MCP access exists only via an unofficial community project. It's ~4 months old with PR-wire-driven star growth, not organic-adoption-driven.
- **HydraDB** genuinely is open source (AGPLv3, confirmed via GitHub API) and its data-model *ideas* (bitemporal edges with `t_commit`/`t_valid`, provenance-by-design) are the closest conceptual match to the brief of anything researched — but the repo is two months old, pre-1.0, has zero tagged releases, and the shipped product wraps a real underlying graph engine behind a single opaque, undocumented REST endpoint. Self-hosting at scale is commercially gated. Betting a "durable" system on it today is the opposite of durable.
- **Letta's MemFS/Context Repositories** is the best *storage-pattern* prior art (git-backed Markdown, structural progressive disclosure, reviewable copy-on-write consolidation) but git-log-as-history is not a queryable temporal model, there's no entity/confidence/decision schema, and capture is agent-mediated only — it doesn't watch the real environment.
- **Zep/Graphiti** has the best temporal/provenance data model of anything researched (`valid_at`/`invalid_at`/`created_at`/`expired_at`, episode-based provenance) — but it's a pure ingestion+reasoning engine with no capture layer, no hierarchy beyond flat tenant tags, and no decision/confidence schema. Also: self-hosting "Zep" itself is no longer possible (Community Edition deprecated) — you'd run Graphiti directly against your own Neo4j.
- **Cognee** has the best integration surface (SDK+REST+MCP+CLI, easiest self-host footprint) and strong retrieval, but updates are destructive-by-default (no historical fact trail unless you opt into a thinly-documented temporal mode), and there's no environmental capture or first-class provenance/confidence field.
- **Mem0 and LangMem** are conversational-personalization tools solving a different problem (what did a user say to a chatbot across sessions) than what this brief needs (what is true about a developer's systems, why, and how confidently) — the mismatch is architectural, not a matter of missing features.
- **Basic Memory** and the **MCP memory-server ecosystem** (official reference server, mcp-memory-service, mcp-memory-keeper) confirm that MCP is a fine transport (genuinely cross-vendor, Linux-Foundation-governed as of Dec 2025) but standardizes nothing about the memory data model — every server invented an incompatible schema, and none has ambient capture, explicit supersession-with-reason, confidence levels, or true nested hierarchy.

## The one requirement no software product solves: capture

Across all nine research passes, **every memory framework is capture-blind** — Letta, Zep/Graphiti, Cognee, Mem0, EverOS, Basic Memory, all three MCP servers: 100% of them require an explicit tool call or file edit to learn anything. None watches git, shell, Docker, or systemd on its own. This is the brief's Section 10-12 "capture layer separate from memory layer" insight validated by the research, not just theorized: the environmental-observation problem and the memory-representation problem are solved (to the extent they're solved at all) by completely different, non-overlapping sets of tools. Capture, by contrast, *is* well-served by mature, boring infrastructure that has nothing to do with "AI memory" branding: Atuin, git hooks, `docker events`, `journalctl -o json`, Watchman. That part of the brief is closer to "assemble existing weekend-grade tools" than "wait for someone to build the right product."

## What's genuinely reusable vs. what must be custom-built

| Layer | Reusable off-the-shelf | Must be custom |
|---|---|---|
| Terminal/shell evidence capture | Atuin (SQLite, harness-agnostic) + shell hooks + Claude Code `PostToolUse` hooks + asciinema (selective) | Correlation ID stitching commands to agent sessions across harnesses |
| Infra/environment evidence capture | git hooks, `docker events`, Docker Drift, `journalctl -o json`, Watchman, `ss`/`/proc` poll-diff | The poll-diff script logic itself; wiring all sources into one append-only event store |
| Non-destructive temporal storage | XTDB (mature bitemporal DB) *or* self-hosted Graphiti (Apache-2.0, if graph/hybrid retrieval wanted out of the box) *or* plain Postgres/SQLite `valid_from`/`valid_to` columns | The specific fact/decision/evidence schema (confidence, supersedes, reason) — no product ships this schema |
| Human-readable hierarchy (Level 0-3) | Basic Memory's Markdown+YAML+observation-category+wikilink conventions, and/or Letta's MemFS directory convention (`system/`, `reference/`, `skills/`) as prior art to imitate | Actual `global→project→component→task` nesting rules; nothing implements this today |
| Consolidation (raw events → derived facts) | Letta's copy-on-write "dreaming" pattern and mcp-memory-service's consolidation module (`contradictions.py`, `decay.py`) as reference designs | The extraction/contradiction-detection logic itself — no product exposes this as an installable component |
| Agent-agnostic query surface | MCP protocol (now vendor-neutral) as transport | The specific tool surface from the brief (`memory.get_current_state`, `memory.get_decisions`, etc.) — every existing MCP memory server has an incompatible, narrower one |

## Bottom line

The lowest-effort path is **not** "adopt product X." It is: wire up the capture layer almost entirely from existing, mature, boring tools (a weekend of work, per both capture research files); pick a mature temporal storage primitive rather than a hyped one (XTDB, or self-hosted Graphiti if graph retrieval is wanted); store the human-facing hierarchy as Markdown using Letta's/Basic Memory's directory and tagging conventions rather than inventing a new format; and write a genuinely small amount of custom code — an extraction/consolidation job and an MCP server with a purpose-built tool surface — because that specific combination (environmental capture + explicit temporal supersession + confidence + decision/rationale + true hierarchy, all in one system) does not exist anywhere in the current landscape. See `PLAN.md` for the concrete architecture and phased build order.
