# EverOS (EverMind-AI) — Research Notes

Sources consulted: GitHub repo (README, docs/overview.md, releases, contributors), evermind.ai/everos and evermind.ai blog, ossinsight.io analytics, DeepWiki mirror, MarkTechPost independent writeup, arXiv paper "EverMemOS: A Self-Organizing Memory Operating System for Structured Long-Horizon Reasoning" (arXiv:2601.02163), the `evermem-claude-code` plugin repo, a third-party `everos-mcp` server (Marvisatron/Glama), and several PR-newswire launch announcements.

## Overview

EverOS is an open-source (Apache-2.0) Python library billed as "one portable memory layer for every AI agent: local-first, Markdown-native, user-owned, and self-evolving." It's built by EverMind, described as a technology-incubation project under Shanda Investment Group (founded by Chen Tianqiao) — i.e. a well-funded startup, not a hobby project. It launched its public beta on **April 14, 2026** (announced via PR Newswire and syndicated to dozens of local-news PR-wire sites — a strong marketing push, worth flagging). By roughly June–August 2026 the GitHub repo had accumulated **~12,000 stars and ~890 forks**, which is fast growth for a ~4-month-old public beta; this looks attributable to heavy PR distribution and an explicit "Global Developer Community Co-Creation Plan" (credits/promotion incentives for contributors) rather than obvious fraud, but it's a hype signal to discount star count against.

Companion/related projects in the same GitHub org (EverMind-AI): **Raven** (self-improving agent harness), **EverAlgo** (extraction/parsing algorithms library that EverOS calls into), **HyperMem** (a separate hypergraph-memory architecture, with a paper accepted at ACL 2026), **EverMemBench/EvoAgentBench** (eval suites), and **MSA** (memory-sparse-attention research). EverOS itself does not implement the hypergraph — that's a distinct project.

Sources: [GitHub - EverMind-AI/EverOS](https://github.com/EverMind-AI/EverOS), [evermind.ai/everos](https://evermind.ai/everos), [evermind.ai](https://evermind.ai/), [ossinsight.io analysis](https://ossinsight.io/analyze/EverMind-AI/EverOS), [MarkTechPost writeup](https://www.marktechpost.com/2026/06/29/meet-everos-an-open-source-markdown-first-agent-memory-runtime-with-hybrid-bm25-vector-retrieval-and-self-evolving-skills/), [arXiv:2601.02163](https://arxiv.org/abs/2601.02163), [PR Newswire launch announcement](https://www.prnewswire.com/news-releases/the-awakening-moment-for-agents-everos-brand-upgrade-and-public-beta-launches-the-era-of-self-evolving-memory-302741954.html).

## How It Works

**Storage stack (three layers, all local by default):**
- **Markdown files** — canonical "truth" source: human-readable, diffable, Git-versionable `.md` files with frontmatter.
- **SQLite** — local state/queue/audit layer (`md_change_state` change queue, cascade audit logs, background-engine state).
- **LanceDB** — vector ANN + BM25 (Tantivy) + scalar filtering for single-query hybrid search.

A background "Cascade Daemon" keeps the Markdown files and the SQLite/LanceDB indexes in sync.

**Memory model (per the arXiv paper and docs/overview.md):** Two parallel tracks:
- **User-track**: Episodes (conversational interactions), Profiles (persistent user traits), Atomic Facts (discrete verifiable statements extracted from episodes), and Foresights (forward-looking inferences/plans tagged with **validity intervals [t_start, t_end]** — this is EverOS's actual temporal-validity mechanism).
- **Agent-track**: Cases (recorded task trajectories) and Skills (procedural knowledge distilled from repeated successful Cases — the "self-evolving skills" claim).

A **MemCell** is the atomic unit: it bundles an Episode + its Atomic Facts + Foresight signals + Metadata (timestamps, source pointers). The lifecycle per the paper is: **Episodic Trace Formation** (dialogue → MemCells) → **Semantic Consolidation** ("Reflection": offline, between-session job that merges/re-extracts related episodes into "MemScenes," updates profiles/skills) → **Reconstructive Recollection** (MemScene-guided agentic retrieval at query time).

**Retrieval**: hybrid BM25 + vector + scalar filtering in one LanceDB query, gracefully degrading based on which provider keys are configured (LLM-only → keyword search; + embeddings → hybrid search + reflection; + reranker → "agentic search" + Knowledge Wiki). Memory is scoped/filterable by `user_id`, `agent_id`, `app_id`, `project_id`, `session_id` — a practical (if flat, not strictly hierarchical) scoping system.

**Configuration tiers**: one OpenRouter API key gets you core memory + keyword search; adding embedding/reranking providers unlocks hybrid/agentic search and a "Knowledge Wiki" (an editable, source-backed CRUD knowledge layer, added in v1.1.0, separate from the episodic memory).

**Claimed benchmarks**: 93.05% on LoCoMo, 83% on LongMemEval, ~90% on a third benchmark, <500ms p95 latency, "~10x lower token cost." These are **EverMind-self-reported**; the one independent write-up I found (MarkTechPost) explicitly caveats: "these numbers come from EverMind posts... verify on your own workload." No independent benchmark reproduction was found.

## Scoring vs the 6 Categories

**1. Capture — Weak for the brief's ambition.** EverOS itself only ingests whatever text/multimodal content (conversations, files, PDFs, images, audio, office docs, URLs) an agent or user explicitly pushes to its `/api/v2/memory/add` endpoint. Confirmed via the official `evermem-claude-code` plugin README: capture is **conversational only** — triggered by Claude Code's `Stop` hook, which extracts the latest user/assistant Q&A pair and uploads it. It explicitly does **not** watch git history/commits, shell command execution, Docker/container state, systemd/services, or filesystem changes outside the conversation. There is no built-in "observer" layer for terminals, git, or system events — anything environmental must be manually fed in by an agent as text.

**2. Representation — Partial.** Has real scoping dimensions (user/agent/app/project/session id) but no explicit global→project→component→task hierarchy. Has a genuine temporal-validity mechanism for one memory type (Foresight validity intervals `[t_start, t_end]`), but ordinary Facts/Episodes don't appear to carry explicit "superseded-at" versioning beyond the Markdown files' own git-diffable history. Metadata includes "source pointers" (basic provenance — links back to originating episode), but I found **no explicit confidence-level field** (confirmed/probable/inferred/unknown) anywhere in the docs, README, or paper. There is **no explicit "decision + rationale" entity type** — the closest analogs are Atomic Facts and Episodes, which are generic, not decision-structured. No first-class relationship/graph model was documented for EverOS itself (the hypergraph approach lives in the separate HyperMem project).

**3. Retrieval — Solid, conventional.** Genuine hybrid retrieval (BM25 + vector + scalar filter in one LanceDB query), scope filtering by the 5 IDs above, and a form of progressive disclosure in practice: the Claude Code plugin's `SessionStart` hook loads a small "recent memories + last session summary" and deeper search happens on demand via `UserPromptSubmit`/`search_memory`. No graph-traversal or multi-hop reasoning was documented for EverOS proper (that's HyperMem territory). Temporal querying is limited to Foresight validity windows, not general point-in-time "what did we believe as of X" queries.

**4. Consolidation — Documented and semi-substantive.** "Reflection" is an explicit offline job that merges/re-extracts related episode clusters into MemScenes and updates Profiles/Skills; Cases→Skills consolidation is the "self-evolving skill" pitch. However, none of the sources describe an explicit **contradiction-detection or fact-supersession algorithm** (how does it know an old fact is now false vs. just old?), and raw evidence retention is implicit only in that Markdown files are kept and Git-versionable — there's no described explicit "evidence log per fact" abstraction.

**5. Integration — Genuinely multi-harness, but bifurcated cloud/self-host.** REST API (`/api/v2/memory/add|flush|search`, `/health`), Python SDK, CLI (`everos init/server start/demo`). Named integrations: Claude Code, Codex, Gemini, OpenCode (via a "Hive" orchestrator), MCP protocol, browser agents ("Ruminer" plugin), TEN Framework (Live2D characters), wearables. **Important nuance found via research**: the *official* EverMind Claude Code integrations — `evermem-claude-code` plugin and `evermemos-mcp` — are **cloud clients**: they require an EverMind API key (`console.evermind.ai`) and route data through EverMind's hosted servers, even though the underlying EverOS engine is self-hostable. A **third-party community developer** ("Marvisatron") built a separate `everos-mcp` stdio server specifically because, in their words, "there was no ready-made MCP" for talking to a purely self-hosted EverOS instance from Claude Code. So: the open-source self-hosted core exists and has a REST API you could wire an MCP server to yourself, but EverMind's own polished, officially-supported Claude Code UX defaults to their cloud, not self-hosting.

**6. Reliability — Good bones, unproven at scale.** Because the canonical store is plain Markdown + frontmatter, it is inherently human-inspectable, diffable, Git-versionable, and hand-correctable — a real strength matching the brief's "human-inspectable/auditable/correctable" requirement. SQLite provides "cascade audit logs." Because storage is just files, it should survive replacement of any single agent harness. That said, the project is ~4 months old in public beta (as of Aug 2026) with rapid point-releases (patch notes mention fixes for "unbounded index growth" and "path-traversal hardening" — i.e., real early-stage bugs being found and fixed), so operational maturity/rollback tooling under real production load is unproven.

## Maturity / License / Effort

- **License**: Apache License 2.0 for the EverOS repo (NOTICE file for third-party attributions). Genuinely open-source, not source-available-with-restrictions as far as I could verify.
- **Cloud vs self-host split**: The core engine (Markdown+SQLite+LanceDB, REST API, CLI) is fully self-hostable and free. EverMind also sells "EverOS Cloud" (Free tier: 3 memory spaces / 50k MCU-month; Pro: 8 spaces / 250k MCU-month, $25/mo post-beta; Enterprise custom) as a zero-ops managed option. The **officially blessed, best-documented Claude Code integration path uses the cloud tier**, not self-hosting — self-hosted MCP integration for Claude Code exists only via a community project.
- **Maturity signals**: ~12k GitHub stars / ~890 forks, but reached that within ~4 months of a heavily PR-wire-marketed public beta launch (April 14, 2026) backed by a well-capitalized investment group — treat star count as a marketing/funding signal more than an organic-adoption signal. Frequent point releases (v1.0.1 → v1.2.3 in a short span) suggest active development and bug-fixing, which is a positive maturity signal even if the absolute age is short. I could not get a reliable contributor-count figure (GitHub's contributor graph did not render in fetches); no independent stat source gave contributor count.
- **Setup effort for a solo dev to self-host today**: Low for the basic engine — `pip install everos`, `everos init`, add one OpenRouter key, `everos server start`, hit the REST API. Getting hybrid search requires an embedding provider key; agentic search/Knowledge Wiki needs a reranker key too. Multimodal ingestion needs an extra `everos[multimodal]` install plus a LibreOffice system dependency for Office docs. Wiring it into Claude Code specifically as a *fully local* setup requires either using the community `everos-mcp` server (not officially maintained by EverMind) or building your own thin MCP wrapper around the REST API — the "5 minutes" setup claim on the marketing site applies to the **cloud** onboarding, not the self-hosted+MCP path.

## Gaps vs the Brief's Vision

- **No environmental/system observation** — it's a passive memory store fed by whatever an agent explicitly pushes; it does not itself watch git, docker, systemd, shell, or filesystem activity. Every "capture" integration found (Claude Code plugin) is Q&A-conversation-only.
- **No explicit confidence taxonomy** (confirmed/probable/inferred/unknown) anywhere in the documented schema — this is a clean miss against the brief's requirement.
- **No first-class "decision + rationale" entity** — closest is generic Atomic Facts/Episodes; decisions and their reasoning would have to be shoehorned into free-text episodes rather than modeled explicitly.
- **No explicit hierarchical scope (global→project→component→task)** — has flat ID-based scoping (user/agent/app/project/session) which can approximate this but isn't the same as a declared hierarchy with inheritance/override semantics.
- **No general graph/relationship model or multi-hop traversal** in EverOS proper — the hypergraph idea lives in a separate sibling project (HyperMem) that is not the same codebase.
- **Provenance is shallow** — "source pointers" in metadata, not a full evidence chain (multiple corroborating/conflicting sources per fact, confidence-weighted).
- **No documented contradiction-resolution algorithm** for when new information conflicts with stored facts — Reflection "merges and re-extracts," but the mechanics of superseding a specific stale fact vs. treating it as historical are not specified.
- **Officially-supported multi-agent story is cloud-centric** — the brief wants something queryable by any future agent without cloud lock-in; EverOS's best-documented path to that (Claude Code plugin) is cloud-based today, undermining the "tool/harness-agnostic and self-hosted" requirement unless you do extra DIY MCP work.
- **Benchmarks are vendor-reported**, not independently verified — treat the "93% accuracy" style marketing claims skeptically until reproduced.

## Verdict

EverOS is a real, technically substantive, Apache-2.0 open-source memory engine — Markdown-as-truth + SQLite + LanceDB hybrid retrieval, a documented MemCell/Episode/Fact/Foresight/Case/Skill schema, and an offline Reflection/consolidation loop — backed by a well-funded team (arXiv paper, ACL-accepted sibling project, real CLI/SDK/REST API), not vaporware, but it is young (public beta since April 2026), its rapid star growth is more a function of PR-wire marketing than organic adoption, its flagship Claude Code integration defaults to EverMind's cloud rather than true self-hosting, and its benchmark claims are self-reported and unverified. Against the brief's specific requirements it is a partial fit at best: it nails progressive disclosure, human-inspectable/diffable storage, and basic hybrid retrieval, but it has no environmental/system observation capability, no explicit confidence taxonomy, no first-class decision+rationale modeling, and only a flat (not truly hierarchical) scope system with no general relationship graph. It's worth considering as **one component in a larger stack** — specifically as the underlying storage/retrieval substrate for conversational/episodic memory (the "what did we discuss and decide" layer) — but it cannot alone satisfy the brief's requirements for capturing system/environmental state, modeling confidence and decision rationale explicitly, or providing a fully self-hosted, harness-agnostic multi-agent query surface without additional custom engineering (a capture layer for git/docker/shell events, a confidence/provenance schema layered on top, and a self-hosted MCP server you build yourself rather than one EverMind ships).
